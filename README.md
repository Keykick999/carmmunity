# 🚗 Carmmunity

> 실제 차량을 튜닝하기 전에 가상의 튜닝 결과를 확인하고, 다른 사용자들과 공유하며 의견을 나눌 수 있는 자동차 튜닝 커뮤니티 플랫폼

**Carmmunity(Car + Community)** 는 실제 차량을 튜닝하기 전 다양한 파츠를 조합하여 결과를 미리 확인하고, 이를 다른 사용자들과 공유할 수 있도록 개발한 자동차 튜닝 커뮤니티입니다.

사용자는 서비스에서 제공하는 차량과 튜닝 파츠를 조합하여 자신만의 차량을 구성할 수 있으며, 완성된 차량을 저장하고 게시글과 함께 공유할 수 있습니다.

또한 댓글, 좋아요, 실시간 채팅, 알림 기능을 통해 다른 사용자들과 자유롭게 의견을 나누고 다양한 튜닝 정보를 공유할 수 있습니다.

---

# 🎯 프로젝트 목표

자동차 튜닝은 실제 작업을 진행하기 전까지 완성된 모습을 확인하기 어렵고, 잘못된 선택은 큰 비용으로 이어질 수 있습니다.

또한 기존 자동차 커뮤니티는 완성된 차량 사진을 공유하는 데 집중되어 있어, 실제 튜닝 결과를 미리 확인하거나 자신의 튜닝 정보를 체계적으로 관리하기 어려웠습니다.

Carmmunity는 이러한 문제를 해결하기 위해

- 가상 차량 튜닝 결과를 미리 확인
- 자신의 차량 튜닝 정보를 저장 및 관리
- 게시글을 통한 튜닝 정보 공유
- 실시간 채팅과 알림을 통한 사용자 간 소통

이 가능한 자동차 튜닝 커뮤니티를 목표로 개발되었습니다.

# 💡 기술적 고민

## 1. DB 상태와 실시간 알림의 일관성 보장

### 문제

DB 트랜잭션이 롤백되더라도 이미 알림이 전송되는 문제가 발생했습니다.

### 해결

`@TransactionalEventListener(phase = AFTER_COMMIT)`을 적용하여 DB 커밋이 완료된 이후에만 이벤트가 실행되도록 변경했습니다.

### 결과

- 데이터와 알림 상태의 일관성 보장
- 롤백 시 잘못된 알림 전송 방지

---

## 2. 서버 장애로 인한 알림 유실

### 문제

DB 커밋 이후 알림 전송 전에 서버가 종료되면 알림이 영구적으로 유실될 수 있었습니다.

### 해결

- 알림 데이터를 동일 트랜잭션에서 `PENDING` 상태로 저장
- Scheduler를 통한 미전송 알림 재전송

### 결과

- 서버 장애 상황에서도 알림 유실 방지
- 최소 1회 이상(at-least-once) 전송 보장

---

## 3. 알림 중복 발송

### 문제

여러 스레드가 동일한 알림을 동시에 조회하여 중복 발송되는 문제가 발생했습니다.

### 해결

- `SELECT ... FOR UPDATE`
- `Propagation.REQUIRES_NEW`

를 적용하여 알림 단위 트랜잭션을 분리하고 비관적 락을 통해 동시성을 제어했습니다.

### 결과

- 중복 발송 방지
- 데이터 정합성 확보

---

# 🔥 트러블 슈팅

| 문제 | 해결 방법 |
|------|-----------|
| DB 롤백 이후에도 알림 발송 | `@TransactionalEventListener(AFTER_COMMIT)` 적용 |
| 서버 장애 시 알림 유실 | `PENDING` 상태 저장 + Scheduler 재전송 |
| 알림 중복 발송 | `SELECT ... FOR UPDATE` + `REQUIRES_NEW` 적용 |
